# 병렬 EDI 최초 실행 브라우저 문제 — 조사 및 진행 메모

- 조사 시작: 2026-08-05
- 구현·자동 검증: 2026-08-06

## 사용자 증상

새 빌드 후 프로그램을 처음 실행하여 공단 EDI 병렬 처리를 시작하면 다음 순서로
실패한다.

1. 1회차: 건강보험·고용보험에서 주소창 없는 이상한 창이 열리고 보안프로그램을
   인식하지 못한다.
2. 그 창을 닫으면 정상 Chrome 창은 다시 보이지만, 실행 중인 자동화는 더 진행하지
   않는다.
3. 2회차: 건강보험·고용보험은 진행되지만 국민연금에서 같은 현상이 발생한다.
4. 3회차에야 세 기관 모두 정상 Chrome으로 동작한다.

## 확인한 원인

### 1. 신규 분리 프로필 3개를 동시에 초기화함

수정 전 `ParallelCliRunner`는 국민연금(9223), 건강보험(9224), 고용보험(9225) CLI를 거의
동시에 시작했다. 각 child는 `WTAX_CDP_PORT` 때문에 일반 사용 Chrome 프로필이 아닌
다음 전용 프로필을 처음부터 만든다.

```text
%LOCALAPPDATA%\원천징수자동화-data\chrome-profiles\cdp-9223
%LOCALAPPDATA%\원천징수자동화-data\chrome-profiles\cdp-9224
%LOCALAPPDATA%\원천징수자동화-data\chrome-profiles\cdp-9225
```

각 Chrome은 같은 초기 대기 뒤 시작했고, CDP `/json/version`이 열리면 포털/보안모듈
준비 여부와 관계없이 성공으로 처리했다. 즉, 새 프로필 생성·Chrome 첫 실행·세 EDI의
보안프로그램 초기화가 한꺼번에 몰린다. 사용자가 관찰한 `1회차 → 2회차 → 3회차`
안정화 패턴과 가장 잘 맞는다.

이 영속 프로필 방식은 기존 변경(`1e54147`)에서 실제 증상 PC의 새 환경으로는 검증되지
않았고, 이후 고용보험(9225)이 추가되면서 최초 3-way 부팅도 별도로 검증되지 않았다.

### 2. 보안 팝업을 작업 탭으로 잘못 선택할 수 있음

국민연금·고용보험의 진입점은 포털 전용 `connect_page`가 있음에도, 기존에는 WEHAGO용
공용 연결기를 호출했다. 공용 연결기는 WEHAGO 탭이 없으면 `context.pages[0]`을
반환한다. 최초 시작 중 `pages[0]`가 보안/확장 팝업 또는 빈 창이면 그 창에 포털 URL을
`goto`하여, 주소창 없는 보안 창이 자동화 작업 창처럼 보일 수 있다.

건강보험은 포털 전용 연결기를 쓰고 있었지만, 목표 URL이 아직 커밋되지 않았을 때
`pages[0]`로 폴백하는 같은 위험이 있었다.

코드에는 `--app`, `--kiosk`, `--headless`처럼 주소창을 없애는 Chrome 옵션이 없다.
따라서 문제 창은 앱이 의도적으로 연 특수 Chrome이라기보다 포털/네이티브 보안모듈
팝업일 가능성이 높다.

### 3. 문제 창을 닫은 뒤 진행이 멈추는 이유

세 포털의 `wait_for_login`은 page/browser가 닫혀 생기는 예외를 무시하고 최대 15분까지
기존 page를 계속 폴링한다. 새 정상 창이 나중에 열려도 실행 중인 CLI는 죽은 page를
다시 연결하지 않으므로 "더 이상 진행 안 함" 상태가 된다.

추가로 각 CLI는 launch/connect/login 실패 시 단순 `return`하는 경로가 있어, frozen
subprocess의 종료 코드가 0으로 남고 GUI가 실패를 완료처럼 보일 가능성이 있다.

## 반영한 코드

1. `src/ui/workers/parallel_cli_worker.py`
   - 준비 마커가 없는 신규 프로필만 **국민연금 → 건강보험 → 고용보험** 순서로
     하나씩 bootstrap한다.
   - 각 기관이 로그인·보안 화면 준비를 마치고, child 종료 코드·stdout 준비 마커·
     프로필 준비 파일이 모두 일치해야 다음 기관으로 진행한다.
   - 세 기관이 모두 준비된 뒤에만 기존의 실제 업무 CLI 3개를 동시에 시작한다.
     따라서 수임처 검색·신고 자료 처리 자체는 계속 3-way 병렬이다.
   - 준비 실패나 사용자의 중단 시 이후 기관 및 실제 병렬 업무를 시작하지 않는다.

2. 각 EDI CLI와 `gui_main.py`
   - `--bootstrap-only` 경로를 추가했다. 국민연금은 Nexacro, 건강보험은 사업장 선택,
     고용보험은 사업장 화면까지 실제 준비가 끝났을 때만 준비 마커를 기록한다.
   - launch/connect/login 실패 또는 예외는 명시적으로 종료 코드 1을 반환하게 했다.
     frozen 실행 파일의 child subprocess도 실패를 성공처럼 표시하지 않는다.

3. `src/automation/nps/_common.py`, `src/automation/nhis/_common_edi.py`,
   `src/automation/comwel/_common.py`
   - 포털 도메인의 정상 탭을 우선 선택하고, 없으면 보안 팝업인 `pages[0]`을 쓰지
     않고 새 일반 탭을 연다.
   - 국민연금·고용보험도 WEHAGO 전용 공용 연결기 대신 각 포털 전용 연결기를 쓴다.
   - 자동화가 붙은 page/CDP 연결이 닫히면 15분 동안 폴링하지 않고 즉시 실패로
     전환한다.

4. `src/utils/chrome_cdp.py` 및 GUI 종료 처리
   - 포트별 로그인·보안 준비 마커를 원자적으로 저장한다.
   - 살아 있을 수 있는 Chrome 프로필의 `SingletonLock` 등을 무조건 삭제하던 동작을
     제거했다. 이 동작은 두 Chrome이 같은 프로필을 동시에 여는 위험이 있었다.
   - GUI 종료 시 병렬 child CLI와 해당 Chrome을 함께 중단·대기한다.
